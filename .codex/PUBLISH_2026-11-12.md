## 1. 进入正确工程，确认分支

```bash
cd "/data/Projects/Unity/Unity_Project/wulaoshi/My project21.5"
git branch --show-current
git status -sb
```

- `cd`：改变当前终端工作目录。路径含空格，必须保留双引号。
- `git branch --show-current`：只查看当前分支，应输出 `release/software-v1.0`。
- `git status -sb`：`-s`显示简短文件状态，`-b`同时显示分支及与远端的领先/落后关系。`M`为修改，`??`为未跟踪文件；不会修改文件。

## 2. 更新远端状态记录

```bash
git fetch origin
git status -sb
```

- `origin`：本地为GitHub仓库保存的远端名称。
- `git fetch origin`：下载远端新提交及更新origin跟踪分支，保留当前工作区，不自动合并、切分支或覆盖代码。
- 再次查看状态：本轮核对时无ahead/behind。执行时若显示behind、分叉或分支不符，先停在这里核对新提交，不在脏工作区直接pull/强推。如果是已知ahead，则检查待推送提交确实属于本次备份。

## 3. 选择本次要保存的文件

```bash
git add -- .codex Assets ExternalCode tests
```

- `git add`：把指定文件当前的内容放入暂存区，准备组成下一次commit；此时仍未上传。
- `--`：标记后面是文件路径，不是Git选项。
- `.codex`：开发记录、现场指南、审查及本教程；`Assets`：Unity代码、资源及相应meta；`ExternalCode`：运行Python及原件参考资料；`tests`：测试源码和测试工程。
- 使用这些目录是因为当前待备份改动均位于其中。若你又改了别的文件，应先核对用途，再单独 `git add -- "实际文件路径"`，不要直接丢弃。
- `ExternalCode`中三份原始压缩包及解压资料也会纳入；部分测试通过解压目录对照原版算法，只暂存顶层Python会漏掉这些依赖。提交前从清单核对是否都属于本次版本。
- 沿用现有 `.gitignore`：Library、Temp、日志、Data、Files、测试生成目录等不会新增提交；原先忽略的大模型和字体也仍不在Git备份中，应保留本机副本。不要用 `-f` 强制加入。
- 父目录新 `SimulationPlatform/`、ZIP和根 `Docs/`不在当前仓库内，本命令不会把老师新UI合入本次快照。

## 4. 检查暂存区

```bash
git diff --cached --name-status
git diff --cached --stat
git diff --cached --check
```

- `--cached`：查看已经选入下一次提交的内容；普通 `git diff` 默认只看尚未暂存的内容。
- `--name-status`：逐项列出路径和A/M/D状态，即新增/修改/删除。确认新脚本与meta成对、Python和测试没有漏掉，没有意外删除或无关资料。
- `--stat`：查看每个文件的增删行数和总体数量，快速判断是否有意外的大范围改动。
- `--check`：检查新增改动的空白问题及冲突标记等；无输出表示这项检查未发现问题，不代表编译通过。
- 输出进入分页器时按 `q` 返回终端。若需要取消某个文件的暂存，可用 `git restore --staged -- "实际文件路径"`，只移出暂存区，保留工作区文件；这不是当前步骤的必执行命令。

## 5. 创建本地提交

```bash
git commit -m "SoftWare1.12测试备份：通信连接、运行数据与柔顺V2（合入新UI前）"
git status --short
```

- `git commit`：把暂存区内容保存成可追踪的本地版本，生成新的提交哈希。
- `-m`：指定提交说明，便于日后查找；文字不是Git标签，也不会修改Unity内部版本号。
- `git status --short`：检查有没有漏下的修改。按当前审查范围，提交后应无输出；若仍有文件，先判断是否属于本版。不要通过reset/删除来追求“干净”。
- 暂存之后如果又编辑了源码，必须重新暂存这些改动再提交，否则commit保存的是上一次add时的内容。

## 6. 上传发布分支

```bash
git push origin release/software-v1.0
```

- 将本地 `release/software-v1.0` 中远端还没有的提交上传到 `origin` 同名分支。这里才真正把源码提交上传到GitHub；不会修改main，也不会自动上传全部标签。
- 如果报 `non-fast-forward`，表示远端状态需要重新核对，先停下，不添加 `--force`。如果报认证/网络错误，保留输出排查，不必反复commit。

## 7. 为这次备份创建并上传新标签

先检查标签名仍未被使用：

```bash
git tag --list v1.12-test.20261112
git ls-remote --tags origin 'refs/tags/v1.12-test.20261112*'
```

- 第一条查本地标签；第二条只读查询GitHub标签，单引号保留通配符交给Git处理。
- 两条都无输出且无错误，才创建下面的新标签。若已有输出，应先核对它指向的提交，不能移动或覆盖同名已发布标签。

```bash
git tag -a v1.12-test.20261112 -m "合入伍老师新UI前的测试源码备份：通信、数据记录与柔顺V2"
git push origin v1.12-test.20261112
```

- `git tag -a`：为当前HEAD创建附注标签，记录说明、作者和时间；标签固定这次已提交的源码，不包含未提交文件。
- `-m`：标签说明，与commit说明相互独立。标签中的日期是备份日期，不表示所有代码都是这一天开发的。
- 第二条：只上传这个新标签，保留旧标签不动。分支push成功而标签push失败时，只重试/排查标签push，不重新提交或重复创建标签。

## 8. 核对上传结果

```bash
git status -sb
git rev-parse HEAD
git ls-remote origin refs/heads/release/software-v1.0 'refs/tags/v1.12-test.20261112^{}'
```

- 第一条：应没有待提交文件和ahead/behind，表示本地发布分支与已知远端一致。
- 第二条：显示当前本地提交的完整哈希。
- 第三条：显示GitHub发布分支和新标签指向的提交；`^{}`将附注标签解引用成commit，因此这两行哈希应与上一步HEAD相同。附注标签对象自己的哈希不同属于正常情况。
- GitHub仓库选择 `release/software-v1.0`，核对最新提交说明；Tags中应有新标签。到此完成源码及标签备份。
