## 一、保存源码并打标签

先保存IDE中修改的文件，退出Unity Play模式并等待导入，确认Console没有编译错误。尚未提交前不要切到别的分支来“搬运”这些未保存的修改。

```bash
cd "/data/Projects/Unity/Unity_Project/wulaoshi/My project21.5"
git branch --show-current
git status --short
git add .
git diff --cached --stat
git diff --cached --check
```

第一条应显示`integration/wulaoshi-21.5-wlj`。检查暂存区包含新C#及对应`.meta`、运行历史资源、`ExternalCode`、测试及`.codex`文档。当前忽略规则会排除Library、Temp、Data、Files等；测试目录对测试用`.csproj`有例外，不会漏掉新测试工程。不要使用`git add -f`强行加入缓存、数据库、大模型或被忽略的现场数据。

确认暂存内容正确后再执行：

```bash
git commit -m "SoftWare1.12测试更新：半自动流程、轨迹采样与运行历史"
git status --short
```

此处`git status --short`应无输出；若仍有修改，先检查来源和是否属于本版，不要继续切分支/打标签。当前提交先属于integration分支，后面合并才让发布分支包含它。

```bash
git fetch origin
git switch release/software-v1.0
git merge --ff-only origin/release/software-v1.0
git merge --ff-only integration/wulaoshi-21.5-wlj
git tag -a v1.12-test.20261028 -m "SoftWare1.12测试更新：半自动流程、轨迹采样与运行历史"
```

解释：fetch更新本机对远端的记录，不改工作代码；第一条merge对齐远端发布分支，第二条将本次已提交结果纳入本地发布分支。`--ff-only`只允许沿现有提交历史前进，不会偷偷做冲突合并。任一步失败就停止，不强推、不重置、不覆盖旧标签。

标签保存的是此时的commit，不包含以后未提交的改动。`-m`是标签说明，独立于commit说明，不影响程序内容或版本号。

## 二、完整构建Linux运行包

使用当前项目与Unity `2022.3.62f2c1`。不修改已有场景YAML、不覆盖旧TEST构建目录。

1. 打开`File → Build Settings`，平台选择`PC, Mac & Linux Standalone`，Target Platform选择`Linux`、Architecture选择`x86_64`；如果平台尚未切换，先Switch Platform并等待完成。沿用项目已有的Scenes In Build。
2. 本轮源码中Unity Player Version仍为`1.9.0`。不影响用Git标签和目录识别本版；如希望改Player Settings中的Version，必须在上面的commit/tag之前修改保存，再把ProjectSettings变更一并提交，不能打完标签后再改版本却仍声称二进制与原标签一致。
3. 点击Build，输出到新目录`/data/Projects/Unity/TEST/TEST1028-v1.12-test/`，文件名例如`SoftWare.x86_64`。不要输出到Assets或项目源码根目录。
4. 等待构建成功；检查整个目录中有可执行文件、`*_Data/`、`UnityPlayer.so`及其余Unity输出文件、`ExternalCode/*.py`、`Assets/微软雅黑.ttf`、`FIELD_COMMISSIONING.md`、`COMMUNICATION_LATENCY.md`。缺文件/构建错误先处理，不能把旧包重命名冒充新版。
5. 做不连接设备的启动/界面检查，并核对源码`git status --short`；若有新的已跟踪改动，不要默认二进制仍对应原标签。运行产生的Data/Files/日志和现场配置保留在私有部署副本中，不带入公开运行包。配置/IP并不等于已验证安全许可；不为检查包而连接/驱动设备。
6. 对只含构建输出、无个人数据库和现场数据的完整目录压缩：

```bash
tar -czf "/data/Projects/Unity/TEST/SoftWare-v1.12-test.20261028-linux-x86_64.tar.gz" -C "/data/Projects/Unity/TEST" "TEST1028-v1.12-test"
sha256sum "/data/Projects/Unity/TEST/SoftWare-v1.12-test.20261028-linux-x86_64.tar.gz"
```

这是运行包，不需要`git add`进源码仓库。工控机旧项目/日志数据库与持久配置须另行备份、核对后迁移，不打入公共附件；先保留新旧程序两个目录，现场监护单目标验收后再决定切换。

构建失败且需要修改源码时，先处理源码/重新提交，再选一个未使用的新标签对应新构建；不要移动已经公开的标签。

## 三、上传原发布分支及本次标签

只有上一阶段完成且确认待发布内容后执行：

```bash
git push origin release/software-v1.0
git push origin v1.12-test.20261028
git ls-remote origin refs/heads/release/software-v1.0 'refs/tags/v1.12-test.20261028^{}'
```

前两条成功表示源码分支与标签已上传，不表示运行包或Release已自动创建。最后两行查询的commit哈希应相同；附注标签的裸哈希不同是正常现象，这里用`^{}`比较它指向的commit。

推送若报non-fast-forward/权限/网络错误，停止并保留输出，不加`--force`。如分支推送成功、标签推送失败，只修复标签推送，不重新commit或重复创建同名标签。
